# 新开会话的交接:验证 → 复述 → 再开工

> 适用于「讨论会话已经把方向聊定,要交给一个全新的执行会话」这一步。
> 目标不是"把我知道的告诉它",而是**让它独立确认这些假设还成立**——然后才允许动手。

## 为什么不能直接派活

讨论会话里的事实,有一半以上是**在旧上下文里成立过的**。新会话没有那个上下文,照单执行有两种失败:
① 它把错的前提当真,做到一半才发现方案不成立;② 它按自己的理解补全细节,跑偏了你却看不出来。

这两条都不是靠"写得更详细"能解决的,只能靠**让它自己验一遍、再用自己的话讲一遍**。

## 三段式

### 第一段:只读验证(不给写权限)

给它的第一份东西不是任务,是**待验证假设清单**。开场必须写明:

```text
本轮不要写代码、不要建仓库。
第一步:完整读 <brief 路径>。
第二步:按 §2 的清单逐条独立验证,每条给出你实际执行的命令或访问的页面 + 关键输出片段。
       不要相信文档里的任何结论,也不要把我的说法当依据。
       如果某条不符,写清楚「不符 + 证据 + 影响」,不要顺着文档说。
第三步:按 §7 的模板复述你的理解。
第四步:停。等我说「开工」再进入计划阶段。
```

### 第二段:复述(它讲给你听)

复述模板要能暴露理解偏差,通常 7 条以内,限字数(例:≤800 字):

1. 一句话:我们要做的是什么(**用你自己的话,不许抄原文**)
2. 它解决什么问题;不解决什么问题
3. 为什么是现在这个定位(而不是相邻的另一个定位)
4. 首个版本的边界:API / 技术路线 / 明确不做的事
5. 第一道门禁各验证什么;任一条失败意味着什么
6. 事实核对:逐条给结论(✅一致 / ❌不符+证据 / ⚠️无法验证+原因)
7. 你认为最可疑、最需要澄清的 3 个点

**第 6 条是重点**:它不是复述你的话,是给出**它自己的核对结论**。第 7 条让你看到它没把握的地方。

### 第三段:门禁通过才开工

复述 + 核对都通过后,才允许:建仓库 / 写计划 / 写代码。
实际案例里,执行会话在第二轮独立复核后**改掉了三条事实、新增了一条**——这三条如果没验,会在第三周才炸。

## 简报(brief)怎么写才叫"假设清单"

每条事实四要素,缺一不可:

```text
### F<n> <一句话断言>
- 方法:怎么验证(命令 / 页面 / 最小实验)
- 预期:验证通过时应该看到什么
- 不符:如果不符合,项目会受什么影响、要做什么
```

**「不符」这一栏是灵魂**。它把"发现错误"从事故变成流程的一部分——执行会话知道发现不符是被期望的行为,而不是"我搞错了"。

简报末尾还要有两块:

- **§复述模板**(见上,固定 7 条)
- **§交流记录(追加式)**:只增不改,每条以 `### YYYY-MM-DD · 角色 · 主题` 开头,结论用 ✅ / ⚠️ / ❌,必须附命令与关键输出。
  这一块就是跨会话信箱,别另开文件。

## 版本分层:先 v0.0.1,再 v0.1.0

**首版计划不要直接叫 v0.1.0。** 0.1.0 是对外承诺"这个东西有个可用的起点";而第一份计划里有一半是待验证假设。

| 版本 | 是什么 | 出口条件 |
|---|---|---|
| **v0.0.1 验证计划** | 假设 + 门禁 + 复述 | 每条假设有验证结论;执行会话复述通过;门禁要么通过、要么明确否掉方案 |
| **v0.1.0 契约** | 里程碑 + 可执行出口条件 | `plan-lint` 0 error;里程碑的验收命令能跑 |

**为什么强调这个**：讨论会话因为"比较了解项目"，很容易**主动提出直接出 v0.1.0**；但对新会话来说，那等于让它对一份自己没验证过的契约负责。人类把首版改叫 v0.0.1，就是在做这个区分——**版本号是承诺，不是进度条**。

## 文档体系:一开始建"骨架与规矩",不建全部文档

逐里程碑长出来的顺序（真实案例）：

| 时机 | 文档 |
|---|---|
| **初始化提交**（必建 5 个） | 文档枢纽 `docs/README.md`、`AGENTS.md`、计划文件、`README.md`、`CHANGELOG.md` |
| 第一个可写的 API 落地 | `SPEC.md`（API 唯一真源） |
| 第一次跨语言/跨进程交互 | ABI / 交叉编译文档 |
| 第一次给出数字 | 基准文档（口径 + 结果） |
| 第一次发布 | 发布门禁清单 |

**一开始真正要建的，是三条规矩**（写进 `AGENTS.md`）：

1. 一条事实只住一个文件，别处只链接（SSOT）。
2. 新增/删除文档必须同步 `docs/README.md` 地图。
3. 代码改了，对应文档同一轮同步。

> 反例：为了"体系完整"先建一堆空壳文档。空壳比没有更伤——后来者会以为契约存在，实际只有一句「实现落定后由本节汇总」。

## 分支:按"回滚需要"决定，不按"会话"决定

| 情形 | 分支策略 |
|---|---|
| 里程碑会改 `main` 上必须能整段回滚的东西（公共 API / CI 门禁 / 发布相关） | **必建** `milestone/Mx-<slug>`，合并用 `--no-ff` |
| 小修复 / 讨论会话自己改文档 | 直接在 `main` |
| 两个子会话**并行**推进不同里程碑 | 各自 `worktree` + 各自分支（否则会互相踩工作树） |
| 只读验证 / 跑探针 / 调研 | 不建分支 |

一条硬约束比"视情况"更管用：**同一工作树同一时刻只有一个写者。**
并行写 = 必须分开 worktree；不并行写 = 一个工作分支就够，不要给每个子会话都造一个分支。

## 一段可复用的开场白

```text
你是 <项目> 的执行会话。本轮不要写代码、不要建仓库。

第一步:完整读 <brief 路径>。这份文档不是命令,是**待验证的假设清单**;里面所有"事实"都可能错。
第二步:按 §2 逐条独立验证 F1–Fn。每条给出你实际执行的命令/页面 + 关键输出;
       不要相信文档结论,也不要把我的说法当依据;不符就写「不符 + 证据 + 影响」。
第三步:按 §7 复述你的理解。
第四步:停,等我说「开工」。

约束:本轮只在临时目录操作;任何一条关键假设不成立,立即停止汇报,不要自行改方案。
```

## 真实案例(匿名化)

> 这套流程第一次跑出成品时的实际形状,数字来自提交历史。

**① 讨论会话里聊定方向。** 方向没定之前不派活。

**② 新开执行会话,第一轮不给写权限。** 给的是「待验证假设清单」:13 条事实,每条四要素
(断言 / 验证方法 / 预期 / 不符时怎么办),末尾附 7 条复述模板。开场白明说:
「不要相信文档里的任何结论,也不要把我的说法当依据」。

**③ 它独立复核 → 改了 3 条事实、新增 1 条。** 其中一条是「预期」本身写错了(把宿主构建与交叉编译混为一谈),
另一条是把「某个工具版本不支持」误当成「这类工具一律不支持」。**没有这一步,这些会在第三周才炸。**

**④ 版本号先降一级。** 讨论会话因为「比较了解项目」,主动提出直接出 v0.1.0;
人类改成 v0.0.1 —— 首版计划一半是待验证假设,撑不起 0.1.0 这个对外承诺。
验证 + 门禁通过后,才升成 v0.1.0 契约。

**⑤ 文档体系只建骨架。** 初始化提交 5 份(枢纽 / AGENTS / 计划 / README / CHANGELOG);
SPEC 在第一个可写 API 的里程碑出现,ABI 与交叉编译在第一次跨语言交互时出现,
基准在第一次给出数字时出现,发布清单在第一次发布前出现。

**⑥ 分支按回滚需要建。** `main` 只收初始化、里程碑合并、发布;每个里程碑一个 `milestone/Mx-slug`,
`--no-ff` 合并。**不是**「每个子会话一个分支」。

最终交付:一个可 `moon add` 的包 + 交叉编译配方 + 可复现的基准表;主会话只做契约、派单、复跑、判定四件事。
