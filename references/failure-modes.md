# 失败模式库

| 症状 | 机制 | 对策 |
|---|---|---|
| 用户说"开始动手"就直接改代码 | 把"动手"当成"跳过计划" | 先产出计划(哪怕 20 行),再问是否执行 |
| 一次派完所有里程碑 | 想省往返 | 一次一个;每个都要有判定点 |
| 子智能体报"测试通过",CI 红 | 它跑的和 CI 跑的不是同一套 | 派单里写死命令;你自己复跑 |
| 改了测试让它变绿 | 没有禁止清单 | 明确"不许改测试/断言" |
| 子智能体顺手改了看板 | 没写"只许改 X" | 看板/台账永远是审核者的 |
| grep 门禁假绿 | 平台默认编码不是 UTF-8 | 显式指定编码,先验证行数 |
| 文件没变却显示已修改 | 换行/stat 缓存 | 用内容判据(diff/hash),别用状态判据 |
| 发布失败后自动重试 | 把不可逆当可重试 | 一次尝试;失败就停 |
| 报告里全是形容词 | 没给汇报格式 | 四件真实输出模板 |
| 事后才发现没验收标准 | 出口条件写成任务名 | 写计划时就跑 plan-lint |

## 一条通用规则

**任何"顺手"都要先问。** 范围外的改动,哪怕只是 typo,也要在报告里列为「发现但没改」,由审核者决定是否单开一单。
